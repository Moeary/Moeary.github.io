## 前言

上一篇 Quest 3 + Unity 的文章写的是怎么把 VR 工程交接给后面的同学。实际带下来还是觉得，Unity 这套对新接手的人太重了：装编辑器、配 Android、装 SDK、连头显、打 APK 再真机调试，每一步都容易卡住。等做项目的人一毕业，后面的人要是没接触过 Unity，很容易就变成“能跑但没人敢改”的祖传工程。

所以我后来换了个思路：干脆先绕开 Unity，直接用 Web 开发把建筑模型、点云或者 3D 高斯泼溅放进网页里，浏览器点开就能看，Quest 3 也能直接从浏览器进 WebXR。

现成的参考案例可以看极客湾的办公室 room tour，他们用无人机配合高斯泼溅把办公室扫下来，做成了能在线逛的互动展馆（`roomtour.socpk.com`）：

- 【欢迎参观极客湾！我们把办公室做成了游戏地图！】<https://b23.tv/BV1Ba7k6AEdF>

![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260609153704.png)

我们不用做得像他们那么复杂，但“现实空间扫描 + Web 交互 + 轻量部署”这条路子完全可以照着走。这篇主要按下面的顺序梳理一遍流程：

1. 为什么在 Unity 之外还要搞一条 Web 路线。
2. Web 3D、点云和 3D 高斯泼溅目前各自适合什么场景。
3. 无人机航拍建筑的拍摄要求与航线安排。
4. 用 RealityScan / RealityCapture 处理航拍素材的大致步骤。
5. 在 Blender 和 `glTF-Transform` 里把模型压到网页跑得动的大小。

![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260609200819.png)

代码实现可以参考我之前做的 Web 端海洋文博馆项目，开源仓库在 <https://github.com/Moeary/Vue_Ocean_Museum> ，线上预览在 <https://oceanmuseum.vercel.app/#/3d> 。里面的 [`OceanScene.vue`](https://github.com/Moeary/Vue_Ocean_Museum/blob/main/src/components/OceanScene.vue) 用 Vue 3 + Three.js 写好了 GLB 加载、PC 鼠标锁定漫游、手机触摸旋转和 Quest 3 WebXR 摇杆移动，后面接手的同学可以直接拿来改模型路径。

## 一、这条路线怎么分工

Unity 完整成熟，适合做重交互的原生 VR 应用；Web 胜在轻量、好发链接。如果项目现阶段主要需求就是看建筑、逛展馆和做点基础交互，每次改一点东西都重新编译安装 APK 实在太费时间了。

![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260610131806.png)

```text
无人机航拍
  -> RealityScan / RealityCapture 处理
  -> Blender 清理、减面、压缩、导出 GLB
  -> Web / Three.js 再压缩处理
  -> 浏览器呈现 3D 场景，必要时接 WebXR
```

![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260610131455.png)

拆成这条流水线之后，组里分工也很清楚：

- 会飞无人机的人负责把建筑素材拍齐。
- 会用 RealityScan 的人负责跑重建出模型。
- 会用 Blender 的人负责清理杂面、减面并导出 GLB。
- 会写前端的人负责把 GLB 放进 Three.js，接好漫游、热点和 WebXR。

刚开始做的时候不用纠结哪个算法更新潮，先把几个实际问题卡死就行：手机浏览器打不打得开？Quest 3 浏览器打不打得开？单个模型能不能压进几十 MB 以内？后面接手的人能不能看懂流程、顺利换上自己的建筑？很多展示项目最后卡住，都是因为导出一个七八百 MB 的模型丢上去，网页加载半分钟直接白屏。先把东西做到能打开、能看、能交接最重要。

## 二、当前 Web 3D 的技术选型

现在商品展示、数字孪生、WebGIS 和线上展馆用 Web 3D 的已经很多了，难点主要在怎么把模型和贴图体积压到浏览器吃得消的范围。

### 1. 主力交付格式还是 glTF / GLB

Web 端交付 3D 资产默认选 `glTF` / `GLB`。Khronos 把 glTF 定位成面向传输和加载的运行时格式，`.glb` 则是把场景 JSON、二进制顶点数据和贴图打进单个文件的二进制包。

Three.js 的 `GLTFLoader` 对 glTF 2.0 及其常用压缩扩展支持得很全：

- `KHR_draco_mesh_compression`
- `EXT_meshopt_compression`
- `KHR_mesh_quantization`
- `KHR_texture_basisu`
- `EXT_texture_webp`

实际做的时候，先拿 RealityCapture / RealityScan 算出建筑模型，再过一遍 Blender 和 `glTF-Transform`（或 `gltfpack`）压网格与贴图，就能得到浏览器加载比较顺畅的 `.glb`。

### 2. 用 WebXR 做轻量 VR 预览

WebXR 最省事的地方是免装 APK。把网页部署到带 HTTPS 证书的域名上（浏览器安全策略要求非本地环境必须走 HTTPS 才能调起 WebXR），拿 Quest 3 自带浏览器打开链接就能进 VR 模式。

Three.js 里接 WebXR 只需要两行核心代码：

```js
renderer.xr.enabled = true;
document.body.appendChild(VRButton.createButton(renderer));
```

当然 WebXR 的局限也摆在那儿：

- 浏览器权限和接口表现受设备影响（不过只做基础前后左右漫游的话问题不大，主流头显基本都兼容类似 Meta Quest 的摇杆手柄映射）。
- 复杂物理碰撞、UI 面板和精细手势交互不如 Unity / Unreal 好做。
- 大体积 GLB 很容易撞上移动头显的内存、GPU 和带宽上限。

所以比较务实的做法是先拿 Web 把模型展示、漫游和轻量在线预览跑通，方便随时发链接给老师和同学看效果；等场景资产打磨得差不多了，再按需迁回 Unity + Meta Quest 工程里写原生插件和自定义 Shader。

## 三、3D 高斯泼溅在项目里的定位

![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260610131545.png)

3D Gaussian Splatting（简称 3DGS）没有走传统三角面片网格那套路子，它用大量带位置、朝向、尺度、颜色和透明度的椭球基元来表示三维场景。

2023 年 SIGGRAPH 的论文《3D Gaussian Splatting for Real-Time Radiance Field Rendering》出来之后，这套方案在实景重建里铺开得很快：

- 直接吃多视角照片或视频抽帧作为输入。
- 训练完能做到实时渲染，比早期 NeRF 路线更适合交互漫游。
- 对树叶、栏杆、雕塑、复杂反光和细碎纹理的还原比传统低模好很多。

极客湾那个办公室展馆之所以看着真实，就是因为 3DGS 把现场原本的杂物细节和光照质感直接留下来了。不过它也有明显的短板：基本没法像传统材质网格那样在引擎里重新打光，拍摄时是什么光照就是什么样，做不了白天切夜景或者开关灯的效果。

另外现阶段往 Web 项目里塞原生 3DGS 还有不少麻烦：

1. 文件格式还没完全统一，`.ply`、`.splat`、`.spz`、`.ksplat`、`.sog` 都在用。
2. 浏览器端得接专门的高斯渲染器，不能直接拿 `GLTFLoader` 读。
3. 碰撞检测、遮挡剔除、尺寸测量和局部编辑都不如传统网格方便。
4. 原始资产体积偏大，不压缩动辄几十上百 MB。

Khronos 在 2026 年 2 月已经放出了 `KHR_gaussian_splatting` 扩展候选，等后续正式普及进 glTF 工具链会好很多。现阶段我们项目没必要死磕各种私有高斯格式，统一转成网格丢进 Blender 后处理再导出 `.glb` 更稳妥。

## 四、无人机航拍建筑的拍摄要求

实景重建非常吃前期拍摄质量，照片本身拍糊了或者视角缺一块，后面换什么重建软件都救不回来。

![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260610132343.png)

航拍实操可以先看这个视频教程：【【全】大型校园无人机倾斜摄影建模指南】<https://b23.tv/BV1W3411s72V>

### 1. 拍摄原则

拍单体建筑时尽量按下面几条来：

1. 相邻照片重叠率保持在 70% 到 85%。
2. 不能只飞正上方俯拍，建筑立面必须补斜向环绕（oblique）视角。
3. 一栋楼至少绕飞 2 到 3 圈：低空立面一圈、中高空斜拍一圈、顶视俯拍一圈。
4. 曝光和白平衡尽量手动锁定，避免相邻角度忽明忽暗。
5. 避开大风、雨雾天、强反光时段以及快速移动的云影。
6. 遇到大面积玻璃幕墙、纯白墙、纯黑墙或重复窗格时，多换几个斜角补拍。
7. 尽量挑人少车少的时间拍，减少画面里的移动物体。

如果手头只有航拍视频，抽帧也能跑：

- 优先用 4K 视频，分辨率比 1080p 富裕很多。
- 抽帧不用太密，先按每秒 1 到 3 帧试。
- 把运动模糊、急转弯和过曝的废帧挑出去删掉。
- 导出抽帧图片时保持原视频分辨率。

### 2. 航线建议

拍教学楼或独立展馆可以按四组航线组合：

| 航线 | 作用 |
|---|---|
| 正射网格 | 获得屋顶和整体平面结构 |
| 45 度斜拍网格 | 获得屋顶边缘、立面上半部分 |
| 环绕立面 | 获得门窗、柱子、墙面纹理 |
| 低空补拍 | 补入口、牌匾、台阶、雕塑 |

如果建筑周边树特别多，树叶这种细碎结构跑传统网格重建很容易糊成一团，用 3DGS 观感会好不少；如果走网格漫游加碰撞路线，直接把周边的树单独替换成简模就行，不用硬把每片树叶都算进高模里。

## 五、用 RealityScan 处理航拍素材

重建软件优先推荐 Epic 免费的 RealityScan，支持照片和视频输入，自动对齐、算高模、减面和烘焙贴图都能在里面走完。软件具体点法看现成的视频和官方文档更直观，这里就不重复贴界面步骤了：

- B 站全流程教程：【RealityScan2.0 + Blender测量摄影 建模、修复、简化发布全流程】<https://b23.tv/BV12guwzdEkL>
- 官方学习中心：<https://dev.epicgames.com/community/realityscan/learning>

需要拿现成校园建筑航拍素材练手的同学，有我联系方式的话可以直接私聊我要。

![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260610132650.png)

在软件里跑通一套标准重建大致就是这七步：

1. 整理并筛选照片或抽帧图片。
2. 导入素材执行相机对齐（Align Images）。
3. 框定有效的重建区域（Reconstruction Region）。
4. 解算高精度网格模型。
5. 在软件内做初步减面简化（Simplify）。
6. 计算展开并生成纹理贴图（Texturing）。
7. 导出 `OBJ` / `FBX` / `GLB`，交给 Blender 做后续清理。

## 六、把建筑模型压到 Web 能跑

RealityScan 直接导出来的模型面数和贴图通常都太大，直接丢进网页根本跑不动，上线前必须过一遍减面和纹理压缩。

### 0. Blender 后处理

先把模型导进 Blender，校准真实比例、坐标原点和正方向，删掉周边飞面与多余地块，把建筑主体控制在 100k 到 500k 三角面左右，重新整理 UV 和贴图后导出成 `.glb`。

### 1. 体积控制目标

单场景文件大小建议按终端设备卡死上限：

| 平台 | 单模型建议大小 |
|---|---:|
| 手机网页 | 10MB 到 40MB |
| PC 网页 | 30MB 到 120MB |
| Quest 3 WebXR | 20MB 到 80MB |
| 校园内网大屏 | 可以更大，但仍建议分块加载 |

压完要是还有两三百 MB，体验还是会很差，尤其是 Quest 3 浏览器本身要跑高分辨率双目渲染，内存和移动 GPU 余量比台式机小得多。

### 2. glTF / GLB 压缩方案

Web 端压 GLB 主要从几何和贴图两头下手：

| 优化 | 作用 |
|---|---|
| Meshopt | 压几何、重排顶点、提升传输和加载效率 |
| Draco | 强几何压缩，体积小，但解码成本更高 |
| KTX2/BasisU | 纹理 GPU 压缩，降低文件体积和显存压力 |

Three.js 的 `GLTFLoader` 都支持这几种扩展，记得在前端代码里配上对应的 Decoder 路径。

### 3. `glTF-Transform` 常用命令

全局安装 CLI：

```bash
npm install --global @gltf-transform/cli
```

先看一眼模型里到底是网格占地方还是贴图占地方：

```bash
gltf-transform inspect building.glb
```

常规 WebP + Meshopt 压缩：

```bash
gltf-transform optimize building.glb building.web.glb --texture-compress webp --compress meshopt
```

贴图改走 KTX2 GPU 压缩：

```bash
gltf-transform optimize building.glb building.ktx2.glb --texture-compress ktx2 --compress meshopt
```

几何面数特别高时也可以试一下 Draco：

```bash
gltf-transform draco building.glb building.draco.glb
```

我自己在 WebXR 场景里更习惯先用 Meshopt + KTX2。Draco 虽然能把文件压得更小，但首屏 CPU 解码耗时有时反而更长，具体选哪个以头显真机加载速度为准。

### 4. 上线前检查清单

压完模型放到页面里之后，按下面几项过一遍：

1. PC 端 Chrome 正常打开，跑一轮开发者工具自带的 Lighthouse，Performance 分数尽量做到 60 分以上。
![](https://raw.githubusercontent.com/Moeary/pic_bed/main/img/20260610132817.png)
2. 手机端浏览器（Chrome / Edge / Safari）能正常加载不闪退。
3. Quest 3 浏览器能正常打开页面。
4. 点进 VR 模式后画面正常显示不黑屏。
5. 摇杆移动时帧率平稳，没有明显卡顿掉帧。
6. 建筑贴图完整无丢失。
7. 地面高度、模型比例和出生点朝向正常。

测试的时候别光在自己带独显的开发机上看，真机和手机跑得顺才算数。

## 七、小结

整条简化下来的建筑上网页流程就是：

```text
无人机航拍
  -> RealityScan 处理
  -> Blender 压缩并导出 GLB
  -> Web / Three.js 再压缩处理
  -> 浏览器呈现场景
```

把这套流程定清楚，主要是方便后面接手的同学复用：换一栋校园建筑、重飞一批照片，顺着跑一遍就能出一个新的在线展馆。先把简化网格、压缩贴图和基础漫游这条主线跑稳，后面有精力再去往上叠点云归档、照片级 3DGS 展示或者回 Unity 深化交互，项目就不容易做着做着烂尾。
