之前写过一篇[替换 Live2DViewerEX 模型贴图的教程]({% post_url 2025-07-14-利用Lpkunpacker解包Live2dviewerEX资源并魔改 %})。整套换装时，找到对应的 PNG 直接替换掉就行。但真想只给袖口添一道花纹，事情反而麻烦：角色身上完整的一件衣服，在原贴图里往往横着、倒着，拆成一堆碎片塞在不同角落。

这次给 LpkUnpackerGUI 加 PSD 导出，就是想解决这个痛点：既然素材已经在模型里了，能不能先整理成方便下笔的 PSD，画完再写回贴图？

最后我做了两条路线：图集 PSD 保留贴图原本的像素排布，姿态 PSD 则把部件拼成角色当前的样子。它们用的是同一批素材，只是组织进 PSD 的方式不一样。

## Cubism Runtime：从参数到网格

Live2D 里的可绘制部件叫 ArtMesh，本质上是一组带连接关系的三角形顶点（mesh）。顶点位置一动，贴在上面的图案就跟着拉伸或弯曲。

模型转头、闭眼、张嘴都对应参数变化。模型师在制作时定义好参数与形变的关系，运行时再按当前参数算出顶点的新坐标。比如把眼睛开合参数从睁眼推到闭眼，眼部网格就会按预设变形。

在[官方的 Cubism Native SDK](https://docs.live2d.com/en/cubism-sdk-manual/cubism-core-api-reference/) 里，上下层分工很明确：Framework 处理动作播放和物理计算，Core 根据参数算出顶点坐标，同时提供 UV、不透明度等绘制数据，最后的渲染器再把纹理贴到三角形上画进窗口。Core 本身只给计算结果，不负责窗口渲染。

连接网格和贴图的是 UV 坐标。每个网格顶点除了在角色画布上有坐标，在贴图上也有对应的取色坐标，三个顶点围成的网格三角形就对应贴图里的一块三角形区域。拿到当前顶点、UV 和三角形索引，就够把部件图像重新拼出来了。这里说的精确是指直接读取模型运行时算出的网格，最终导出的像素图像还是会受采样精度和重映射方式影响。

## 在 Python 里调用 Core 拿姿态数据

Cubism Core 在 Windows 下是一个编译好的 DLL 动态库，通过 Python 自带的 [`ctypes`](https://docs.python.org/3/library/ctypes.html) 声明好函数参数和返回值类型，就能直接在 Python 里调 C 接口取回网格数据。

导出流程大体分四步：

1. 加载模型：找到兼容的 Core DLL，读取 `.moc3`，校验数据并分配运行时内存。
2. 设置姿态：写入导出时刻的参数值，调用 `csmUpdateModel` 更新网格。
3. 读取部件：取出每个 ArtMesh 的顶点、UV、三角形索引，以及贴图编号、绘制顺序和裁剪蒙版关系。
4. 拷贝数据：把原生内存里的数组拷贝到 Python 侧保存，交给后续的图像重建。

第四步很容易踩坑。DLL 返回的不少字段是裸指针，在模型释放或者下一次 `csmUpdateModel` 之前，必须按元素类型和长度把数据真正拷出来，只存指针地址留不住导出那一刻的姿态。同样，导出姿态 PSD 时也得把预览窗口当时的参数一并传进去，否则新开实例走默认参数，导出来的动作就对不上了。

拿到数据之后，Python 侧用 NumPy 整理数组，用 OpenCV 做三角形之间的像素映射，最后写成 PSD 图层。整条导出链路都在 CPU 上跑，和预览窗口用的 [live2d-py 原生封装](https://github.com/EasyLive2D/live2d-py/blob/main/CONTRIBUTING.en.md) + OpenGL 渲染互不干扰。

## 第一条路线：图集 PSD

### 导出：按 UV 抠出部件

图集 PSD 从选中部件的 UV 出发，定位它在原贴图里用到的区域，单独放进 PSD 图层。

取图的时候不能直接截外接矩形，因为图集里的碎片排得很密，矩形框里经常混着别的部件。程序会先按 UV 三角形生成一张像素掩码，只保留三角形覆盖到的像素，外围全部留透明。

抠出来的部件可以留在原图位置，也可以做紧凑排版减少空白。紧凑排版只平移图层在 PSD 里的坐标，不旋转也不缩放，原来一像素导出后还是一像素，同时在元数据里记下它来自哪张贴图的哪个坐标。这样导出来的袖子可能还是歪着或倒着的，不会跟着角色抬手弯曲，但原始像素细节保留得最完整。

### 回写：改过的像素直接放回原位

假设在袖口画了一条红边。回写时程序会对比编辑后的图层和导出时存下的原图，找出有效区域内颜色或透明度发生变化的像素，按记录的偏移坐标直接写回原贴图。

哪怕导出时用了紧凑排版把袖子挪到了 PSD 左上角，回写依然会落回原图集的位置。由于全程没有几何形变和重采样，改细线、文字、小图案或者修透明边缘时不会发糊。缺点也很直观：碎片是散的，画完是什么上身效果得回模型预览里看。

## 第二条路线：姿态 PSD

### 导出：把贴图三角形映射到当前姿态

姿态 PSD 除了用 UV，还会用上 Core 算出来的当前顶点坐标。

比如袖子上的一个小三角形，在原贴图里是平的，角色抬手之后在画面里被拉斜了。已知贴图三角形和姿态三角形各自的三个顶点坐标，就能算出它们之间的仿射变换（平移、旋转、缩放与错切），把贴图里的像素搬到当前姿态对应的位置。整只袖子没法靠一次全局变换还原，拆成成百上千个小三角形逐块映射就能拼出完整部件。

实际算的时候还要统一坐标系：Core 里的模型坐标要按画布原点和缩放比例换算成像素坐标，归一化的 UV 坐标也要乘上贴图宽高并处理上下翻转。除此之外还得带上绘制顺序、部件不透明度和裁剪蒙版（比如眼球只显示在眼眶范围内），哪怕只导出几个选中部件，计算裁剪依赖的其他遮罩部件信息也得一并读出来。

这样生成的 PSD 跟预览窗口里看到的姿势一致，适合直接在角色身上排花纹位置、调大小和试整体配色。

### 回写：做差量反向映射

姿态 PSD 回写要把画在当前姿势上的修改，顺着导出时记录的三角形映射反推回原始图集。

麻烦的地方在于图像先正向拉伸一次、再反向压回去一次，重采样会让细线变软、边缘轻微发虚。如果每次回写都把整个部件重新压回贴图，连没动过的地方也会跟着糊掉。所以我这里用了差量回写，只提改动部分再映射回去：

```text
改动 = 编辑后的图层 − 导出时保留的原样
新贴图 = 原贴图 + 映射回去的改动
```

上面只是简化写法，实际代码里还要约束有效写入掩码并拆开处理透明度。举个例子，某个袖子部件在运行时本身设了 50% 不透明度，回写时不能把这层运行时半透明又烤进贴图里，否则重新加载模型再乘一次透明度就更淡了。导出时存下来的裁剪与不透明度参数，就是为了把“模型渲染效果”和“贴图本身的像素修改”分开。

完全没动过的选区 PSD 会直接复用原 PNG；有改动时也只覆盖发生变化的区域。当然差量回写也不是无损的：在当前姿态下被挤得很窄的三角形、过低的导出分辨率，或者被遮挡完全不可见的区域，反向映射都会丢精度，遇到特殊混合模式时 PSD 预览和原生渲染也会有出入，画完还是要回模型里核对一遍。

## 两条路线共有的限制

不管走哪条路线，导出时都会附带一份配套元数据，记着部件映射关系、图层框位置和比对用的基准图。回写依赖这份对应关系，所以在原有绘画组里改像素没问题，但如果直接在画布上移动或缩放了整个部件图层，位置绑定就断了，程序会直接拒绝回写。

另一个绕不开的问题是共享 UV。有些模型里左右对称或者复用的两个部件看起来各自独立，导出到 PSD 也能分成两个图层，但底层其实读的是贴图上同一块像素区域。改了其中一个，另一个在模型里也会跟着变。回写前需要检查改动区域有没有波及未选中的部件。

说到底，这套导出重建的是方便改图的 PSD，恢复不了模型作者最初的绘画分层或 `.cmo3` 源工程，运行时资源里没存的创作信息是拿不回来的。

## 两种方式的取舍

| 对比项 | 图集 PSD | 姿态 PSD |
| --- | --- | --- |
| 图层中的形状 | 原贴图中的部件形状 | 当前参数下的部件形状 |
| 导出的主要处理 | 沿 UV 范围取图，记录原位置 | 将 UV 三角形映射到姿态三角形 |
| 回写的主要处理 | 将变化写回原像素位置 | 将变化经三角形映射送回图集 |
| 更适合的修改 | 细线、文字、小图案、像素边缘 | 花纹布局、装饰轮廓、整体配色 |
| 主要限制 | 素材零散，不容易判断上身效果 | 存在重新取样，受姿态与分辨率影响 |

实际改图时两条路线可以混着用：先导出姿态 PSD 在角色身上定好花纹位置和大块配色，再切图集 PSD 把边缘细线和文字修干净。
